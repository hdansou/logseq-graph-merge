logseq-graph-merge · design draft

How several DB graphs become one

The merge copies journals onto the same date and appends pages that match an existing one. Tags and properties are reconciled before any content moves, and assets are copied with their checksums verified. Every merge rule lives in a pure planner, so the same sources in the same order always produce the same merged EDN.

2026-09-14 · matches the implementation · first verified 5-graph merge

  1. 1PreflightSources exist, destination is new, schema versions match
  2. 2ExtractRead-only export plus page and asset identity queries
  3. 3PlanEleven stages over data; no I/O
  4. 4ValidateIn-memory import, plus asset checksums
  5. 5WriteImport into a new graph, copy assets
  6. 6VerifyEvery page has its blocks, assets match, then graph validate

End-to-end pipeline

Nothing is written until the merged EDN passes validation in memory. The count check after import is required: in the spike, graph import rejected an EDN file, wrote nothing, and still exited 0 with “Imported”. The two identity queries exist because the export drops page parents and unreferenced uuids.

Tags and properties: reconcile first

The same property name gets a different random ident suffix in each graph, so matching goes by title. The first source in the list sets the schema. A later property with a different type or cardinality becomes title (graph) instead of silently colliding.

Page matching

Pages are grouped first and resolved second, so the result does not depend on which source a tagged page came from. Source order only decides which uuid, title spelling and properties win.
